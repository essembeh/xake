# Xake — MVP : jouer contre la machine avec analyse

> Web app d'apprentissage des échecs : partie contre un moteur au Elo réglable, analyse Stockfish
> à chaque coup, navigation dans un arbre de variantes avec marque-pages, parties sauvées dans le
> navigateur. Utilisable sur desktop et installable sur l'écran d'accueil iOS (PWA).
>
> Statut : **validé, MVP implémenté** (étapes 0 à 6). Rédigé le 2026-10-28.

## 2. Architecture

> **Remplacé le 2026-10-30** : Stockfish ne tourne plus que dans le navigateur (spec 005 §10).
> Les règles d'analyse ci-dessous (infos exactes, profondeur complète) s'appliquent telles quelles
> à `js/engine.js` ; le pool et le `lifespan` serveur n'existent plus.

```
 navigateur (PWA)                                    serveur (stateless)
┌──────────────────────────────┐   POST /api/move    ┌────────────────────────────┐
│ chessground (plateau, touch) │ ──────────────────▶ │ FastAPI                    │
│ chess.js (règles, SAN, PGN)  │   POST /api/analyse │  ├─ validation python-chess│
│ arbre de coups + marque-pages│ ──────────────────▶ │  └─ EnginePool             │
│ localStorage (parties)       │ ◀────────────────── │      ├─ pool "play"  (Elo) │
│ service worker (app shell)   │   JSON              │      └─ pool "analyse"     │
└──────────────────────────────┘                     │         N × stockfish (UCI)│
                                                     └────────────────────────────┘
```

- **Tout l'état de partie vit dans le client.** Chaque requête porte la position complète :
  `start_fen` + liste des coups UCI depuis cette position (l'historique sert au moteur pour la
  détection des répétitions et de la règle des 50 coups ; une FEN seule les perd).
- **Pool de processus Stockfish longue durée**, créé dans le `lifespan` FastAPI : lancer un
  process par requête coûte le démarrage + le chargement NNUE (à mesurer, ordre de 100 ms). Un
  `asyncio.Queue` d'engines ; la taille du pool borne la concurrence (et donc la charge CPU).
- **Analyse** : seules les infos UCI exactes sont retenues (les infos `lowerbound`/`upperbound`
  portent une PV tronquée à un coup), puis les lignes sont triées pour le camp au trait.
- **Deux pools distincts** : `play` (bridé par Elo, reconfiguré à chaque requête) et `analyse`
  (pleine force, `MultiPV`). Évite de basculer `UCI_LimitStrength` en permanence sur le même
  process et d'oublier de le remettre.
- « Stateless » au sens HTTP : les engines gardent leur table de hachage entre deux requêtes, sans
  impact fonctionnel. Un engine qui crashe est retiré du pool et relancé.

## 3. API

> **Remplacé le 2026-10-30** : Stockfish ne tourne plus que dans le navigateur (spec 005 §10).
> Plus d'appel HTTP : `js/engine.js` garde le même contrat (position, réponses, scores du point de
> vue des Blancs, mêmes fins de partie que le plateau (spec 005 §11), erreurs en `EngineError`). Seuls
> `/api/version` (sonde de readiness) reste côté serveur ; `/api/health` est supprimé (spec 005 §11).
> Puis plus de serveur du tout (spec 007).

Toutes les positions sont décrites par :

```json
{ "start_fen": "<FEN ou null pour la position initiale>", "moves": ["e2e4", "e7e5"] }
```

Validation côté serveur (python-chess) : FEN valide, coups légaux en séquence → sinon `422`.

### `POST /api/move` — coup de la machine

Requête : position + `elo` (400–3190) + `movetime_ms` optionnel (borné par les settings).
Réponse : `{ "uci": "g1f3", "san": "Nf3" }`. Position terminale → `409`.

### `POST /api/analyse` — évaluation + meilleurs coups

Requête : position + `multipv` (1–5) + `movetime_ms` optionnel.
Réponse :

```json
{
  "score": { "cp": 34, "mate": null },
  "depth": 18,
  "lines": [
    { "uci": "g1f3", "san": "Nf3", "score": { "cp": 34, "mate": null }, "pv_san": ["Nf3", "Nc6", "Bb5"] }
  ]
}
```

- **Scores toujours du point de vue des Blancs** (ce que la barre d'éval consomme directement).
- Position terminale : `lines` vide, `score` = mat ou nulle.

### `GET /api/health`

Vérifie qu'au moins un engine répond (`isready`). Sert de probe k8s.

### Bornes (settings)

`movetime_ms` max, `multipv` max, tailles de pool, timeout d'acquisition d'un engine → `503`
si le pool est saturé au-delà du timeout. Ce sont les seuls garde-fous de charge : sans auth, un
client peut saturer le CPU (§10).

## 4. Elo → options UCI

> Table appliquée par `js/engine.js` (seule implémentation depuis 2026-10-30) ; les bornes
> 400–3190 restent vérifiées par `XAKE_DEFAULT_ELO`.

| Elo demandé | Options |
| --- | --- |
| 1320 – 3190 | `UCI_LimitStrength=true`, `UCI_Elo=<elo>` |
| < 1320 | `UCI_LimitStrength=false`, `Skill Level=0` + limite de `nodes` interpolée en log (400 → 20, 1320 → 5000) |

- La calibration de `UCI_Elo` par Stockfish est faite à une cadence longue ; avec un `movetime`
  court le jeu est plus faible que l'Elo annoncé. **Les valeurs affichées sont indicatives.**
- Dans Stockfish 18, `UCI_Elo=1320` correspond déjà à `Skill Level` 0 : en dessous, seule la
  privation de nœuds affaiblit le jeu. **Calibration à faire** (parties contre un adversaire de
  référence). `Skill Level` bas joue « bons coups + bourdes aléatoires », peu humain. Évolution identifiée :
  **Maia** (lc0 + poids entraînés sur parties humaines 1100–1900) comme moteur `play` alternatif ;
  l'abstraction de pool doit le permettre sans toucher au reste.
- ~~**Elo modifiable à tout moment**~~ : depuis le 2026-10-30, le niveau se choisit avec l'adversaire
  à la nouvelle partie seulement (spec 006 §4), il n'est plus dans les réglages.
  L'Elo est mémorisé sur chaque nœud joué par la machine (affiché dans l'historique, exporté en
  commentaire PGN).

## 5. Stockfish : fourniture du binaire

> **Remplacé le 2026-10-30** : Stockfish ne tourne plus que dans le navigateur (spec 005 §10).
> Plus de binaire : ni dans `shell.nix`, ni dans l'image, ni en CI. stockfish.js est vendorisé
> (`scripts/vendor.sh`).

- Dev (NixOS) : `stockfish` fourni par `shell.nix` (chargé par direnv, `use nix`), chemin configurable via
  `XAKE_STOCKFISH_PATH` (défaut : `stockfish` dans le `PATH`).
- Image : binaire Stockfish dans le `Dockerfile` (paquet Debian ou release officielle épinglée —
  à trancher à l'étape de conteneurisation, le paquet Debian est souvent en retard d'une version).
- Les tests d'API tournent contre le vrai Stockfish (pas de mock) et sont `skip` si le binaire est absent.

## 6. Fonctionnalités front

### 6.1 Nouvelle partie

Choix : couleur (Blancs / Noirs / aléatoire), Elo de départ, position de départ (initiale ; FEN
collée en option). La partie précédente est déjà sauvegardée (§7), rien à confirmer.

La couleur se choisit sur trois tuiles : pion blanc, pion mi-blanc mi-noir (aléatoire), pion noir,
dans le jeu de pièces choisi, sur la même pastille couleur case que les pièces prises (002 §1).
Sélection en bordure accent. Elles remplacent une barre segmentée texte, peu parlante.

Elo proposé : le dernier choisi dans ce navigateur (`prefs.elo`, `localStorage`) ; à la première
visite, `XAKE_DEFAULT_ELO` (400–3190, défaut 1500, servi par `/config.js` comme la langue).

### 6.2 Jeu contre la machine

- Après mon coup, le client appelle `/api/move` puis `/api/analyse` sur la nouvelle position.
- Délai minimal d'affichage du coup machine (~300 ms) pour qu'il reste lisible.
- Requêtes en vol annulées (`AbortController`) dès que la position affichée change : navigation
  rapide dans l'historique = pas de réponses obsolètes appliquées.

### 6.3 Analyse

- **Barre d'évaluation verticale à gauche du plateau**, orientée selon le plateau (mon camp en bas).
  Conversion cp → % par sigmoïde (formule Lichess : `50 + 50 * (2 / (1 + exp(-0.00368208 * cp)) - 1)`),
  mat = 100 %/0 % avec libellé `M3`.
- **Meilleurs coups** (1 à 5, réglable) : liste avec score + variante principale en SAN, et
  **flèches sur le plateau** (shapes chessground, épaisseur décroissante par rang). Tap sur une
  ligne = jouer ce coup.
- Toggle « masquer l'analyse » pour réfléchir sans indice ; l'analyse reste calculée, seul
  l'affichage change.
- L'analyse porte sur la **position affichée**, y compris en naviguant dans l'historique.

### 6.4 Je joue les deux camps

Toggle : activé, la machine ne joue plus, je déplace les deux couleurs (analyse toujours active).
Désactivé, si c'est au tour de la machine sur la position affichée, elle joue.

### 6.5 Historique, navigation, annulation, variantes

La partie est un **arbre de coups**, pas une liste : revenir en arrière puis jouer un autre coup
crée une variante sans rien perdre.

```
Node { id, parent_id, uci, san, fen, by: "me" | "engine", elo?, children: [id…] }
```

- Ligne principale = premier enfant ; la liste de coups n'affiche que la ligne parcourue, les
  alternatives d'un coup sont écrites à côté de lui (spec 002 §10).
- **Navigation** : ◀ ▶ (et ⏮ ⏭), flèches clavier sur desktop, tap sur un coup de la liste. Naviguer
  ne modifie jamais l'arbre. Depuis une position passée (qui a déjà une suite), je peux jouer
  **quel que soit le camp au trait**, sans passer en mode deux camps : nouvelle branche (ou on suit
  la branche existante si le coup y est déjà). Si je remplace un coup de la machine, c'est ensuite
  à moi de jouer, puis la machine reprend normalement sur la nouvelle branche.
- **Annuler** (takeback) : supprime mon dernier coup **et** la réponse de la machine (2 demi-coups,
  1 en mode deux camps) **si ce sont des feuilles** ; sinon (des variantes en partent) ça se
  contente de reculer. Pas de confirmation, mais un « refaire » immédiat (toast) tant qu'aucun
  coup n'a été joué depuis.
- Promotion : sélecteur de pièce (chessground ne le fournit pas, petit overlay à faire).

### 6.6 Marque-pages

- Bouton 🔖 : marque la position affichée (nœud), avec un libellé optionnel (défaut : `12. Nf3`).
- Liste des marque-pages de la partie ; tap = sauter au nœud. Supprimer un marque-page ne touche
  pas l'arbre ; supprimer une branche (annulation) supprime les marque-pages qui y pointaient.

### 6.7 Parties précédentes

Liste (date, couleur, Elo, résultat ou « en cours », nombre de coups) → reprendre, renommer,
exporter, supprimer. Tri par dernière modification.

- **Supprimer** (✕) : immédiat, sans confirmation. **Désactivé sur la partie en cours** : la
  supprimer la remplaçait aussitôt par une partie neuve et vide, avec le même titre, et l'on
  croyait la suppression sans effet. Pour la supprimer, ouvrir ou commencer une autre partie.

- **Renommer** (✎) : nom libre stocké dans `Game.name`, affiché à la place du titre généré
  (« Blancs contre Stockfish 1500 »). Vide, ou égal au titre généré : retour au titre généré.
  Renommer ne touche ni `updated_at` (l'ordre de la liste ne bouge pas) ni la partie courante.
- Le nom part dans l'en-tête PGN `Event` (défaut `xake`) et revient à l'import. Il n'est pas
  dans le lien de partage (fragment d'URL gardé court).

## 7. Persistance (localStorage)

- Une clé par partie `xake:v1:game:<id>` (sauver un coup ne resérialise pas tout
  l'historique), `xake:v1:current`, `xake:v1:prefs` (Elo par défaut, multipv,
  toggles, thèmes). Le préfixe de version permet une migration explicite plus tard.
- `Game { id, name?, created_at, updated_at, player_color, start_fen, elo, nodes, root_id, current_id, bookmarks, result }`
- Sauvegarde à chaque modification. Ordre de grandeur : une partie avec variantes
  fait quelques dizaines de Ko, le quota (~5 Mo) laisse de la marge pour des centaines de parties ;
  `QuotaExceededError` attrapée et signalée.
- **Export / import PGN** (variantes et marque-pages en commentaires) : c'est le seul moyen de
  sauvegarde et de transfert entre appareils (§8, risque iOS).

## 8. Mobile & PWA iOS

### Ergonomie

- **Portrait mobile** : plateau pleine largeur (moins la barre d'éval, ~10 px), en dessous une
  barre de contrôles (⏮ ◀ ▶ ⏭ · annuler · 🔖 · menu), puis meilleurs coups, puis historique.
  Réglages (Elo, couleur, multipv, toggles) dans une **bottom sheet**, pas dans la page.
- **Desktop / paysage** : plateau à gauche, panneau à droite.
- Cibles tactiles ≥ 44 px, `touch-action: manipulation` (pas de zoom double-tap),
  `overscroll-behavior: none` (pas de pull-to-refresh pendant un drag), pas de sélection de texte
  sur le plateau. Jeu au tap (case départ → case arrivée) **et** au drag, natif chessground.
- Swipe horizontal sur la zone sous le plateau = coup précédent / suivant (à valider à l'usage).
- Slider d'Elo par pas de 50 avec valeur affichée ; changement pris en compte au coup suivant.

### Thèmes

- UI : Auto (suit le système) / Clair / Sombre, appliqué avant le premier rendu.
- Plateau : 6 palettes (cases dessinées en `repeating-conic-gradient` sur des variables CSS).
- Pièces : 4 jeux Lichess vendorés, **tous sous licence libre** : `cburnett`, `merida` (GPLv2+),
  `mpchess` (GPLv3+), `pixel` (AGPLv3+). Les jeux CC BY-NC-SA (`california`, `maestro`,
  `cardinal`, `staunty`) ont été retirés le 2026-10-28 : usage non commercial seulement. Un choix
  stocké vers un jeu retiré retombe sur `cburnett` au chargement.

### PWA

- `manifest.webmanifest` : `display: standalone`, `orientation: portrait`, icônes **PNG
  seulement** 180/192/512 (+ `<link rel="apple-touch-icon">` 180×180), `theme_color`. Pas de SVG
  dans le manifest : iOS ne sait pas en faire une icône d'écran d'accueil. Le SVG reste la favicon.
- **Icônes à la racine** (`routers/web.py`) : à l'ajout sur l'écran d'accueil, iOS sonde
  `/apple-touch-icon.png`, `-precomposed`, `-240x240(-precomposed)`, en plus de l'icône déclarée.
  Ces 404 donnaient un « X » gris (constaté dans les logs). Toutes ces variantes servent le PNG
  180×180, `/favicon.ico` le PNG 192 ; cache d'un jour.
- **Favicons PNG** 192/512 déclarées à côté du SVG : Firefox iOS fait son raccourci d'écran
  d'accueil à partir de la favicon (il ne demande ni `apple-touch-icon` ni les chemins racine,
  constaté) et ne sait pas utiliser le SVG.
- `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">`,
  `apple-mobile-web-app-capable`, `apple-mobile-web-app-status-bar-style`, marges via
  `env(safe-area-inset-*)` (encoche, barre home).
- Service worker **network-first** : toujours à jour en ligne (pas de version de cache à bumper),
  l'app shell en cache permet de lancer l'app hors ligne ; l'API n'est jamais cachée. Hors ligne :
  toast « moteur indisponible » avec réessai, le mode deux camps reste utilisable.
- **Cache dès le premier lancement** (2026-10-30) : le premier chargement se fait avant que le
  service worker contrôle la page, donc rien n'était mis en cache ; l'app installée sur iOS ne
  démarrait pas en mode avion tant qu'elle n'avait pas été relancée en ligne (cache vide constaté
  après une visite, Chromium et WebKit). La page envoie au worker la liste de ce qu'elle a chargé
  (`performance.getEntriesByType("resource")` + la page), qu'il met en cache aussitôt. Toute
  navigation hors ligne sans entrée en cache retombe sur la page principale. Écarté : une liste de
  fichiers à précharger écrite dans `sw.js`, à maintenir à la main à chaque nouveau module.
- **`Cache-Control: no-cache`** sur les fichiers statiques (2026-10-30) : sans cet en-tête, le
  navigateur estime lui-même une durée de vie et peut exécuter un ancien `main.js` après un
  déploiement, service worker compris (il passe par le cache HTTP). Revalidation par `ETag` :
  un `304` sans corps quand rien n'a changé. `/config.js` et les icônes gardent leur propre en-tête.
- **HTTPS obligatoire** pour le service worker → derrière l'ingress TLS du homelab.
- Libs front **vendorées** dans `static/vendor/` (versions épinglées) plutôt que chargées depuis
  un CDN : pas de dépendance réseau tierce au lancement, cache SW simple. Depuis la spec 007 :
  paquets npm regroupés par Vite, toujours servis par le site lui-même.

### Risques iOS

- Le stockage d'une app installée sur l'écran d'accueil est **séparé de celui de Safari** et
  **supprimé avec l'icône**. WebKit exempte a priori ces apps de l'éviction à 7 jours, mais je ne
  le garantis pas → l'export PGN (§7) est le filet de sécurité, à ne pas reporter.
